# 요구사항정의서 — 외부 인증 프로바이더 이메일 도메인 적용 범위

- 작성일: 2026-08-14
- 작성자: Jinho Lee
- 상태: 초안 (승인 대기)

## 1. 문제 정의

현재 외부 인증 프로바이더(`ExternalAuthProvider`)의 적용 범위는 **클라이언트 단위**로만 지정할 수 있다.

- `client_id`가 `NULL`이면 테넌트 전체 클라이언트에 적용된다.
- `client_id`에 값이 있으면 해당 클라이언트 인증 시에만 적용된다.
- `ExternalAuthService.checkDuplicate()`가 `(tenant_id, client_id)` 조합당 프로바이더를 **1개만** 허용한다.

이 구조에서는 **같은 클라이언트로 로그인하는 사용자를 이메일 도메인에 따라 서로 다른 외부 인증 시스템으로 보낼 수 없다.**

실제 요구되는 사용 형태는 다음과 같다.

```
로그인 계정 user@test1.com  → 조직 A의 외부 인증 서버
로그인 계정 user@test2.com  → 조직 B의 외부 인증 서버
그 외 도메인               → 도메인 무관 프로바이더 또는 로컬 인증
```

즉, 하나의 테넌트/클라이언트 아래에 **여러 외부 인증 프로바이더를 등록하고 로그인 이메일의 호스트명으로 분기**해야 한다.

## 2. 목표

- 외부 인증 프로바이더 적용 범위 조건에 **이메일 도메인(호스트명)** 을 추가한다.
- 하나의 프로바이더에 **여러 도메인**을 등록할 수 있게 한다.
- 클라이언트 범위 조건과 도메인 조건이 **함께** 동작하도록 우선순위를 정의한다.
- 기존에 등록된 프로바이더의 동작을 **변경하지 않는다**(완전 하위호환).

## 3. 기능 요구사항

| ID | 요구사항 |
|----|----------|
| FR-1 | `ExternalAuthProvider`에 적용 대상 이메일 도메인 목록 필드(`emailDomains`)를 추가한다. 값이 없으면(`null`/빈 배열) 도메인 무관으로 취급하여 기존과 동일하게 동작한다. |
| FR-2 | 한 프로바이더에 여러 도메인을 배열로 등록할 수 있다. 예: `["test1.com", "test1.co.kr"]` |
| FR-3 | 도메인 매칭은 **정확 일치**이며 **대소문자를 구분하지 않는다**. 서브도메인 자동 매칭이나 와일드카드(`*.test.com`)는 지원하지 않는다. `corp.test1.com`을 매칭하려면 해당 값을 명시적으로 등록해야 한다. |
| FR-4 | 도메인 저장 시 정규화한다: 앞뒤 공백 제거 → 소문자 변환 → 선행 `@` 제거(`@test.com` 입력 시 `test.com`으로 저장). 정규화 후 중복 값은 제거한다. |
| FR-5 | 정규화 후 도메인 형식이 유효하지 않으면 400 오류를 반환한다. |
| FR-6 | 로그인 시 프로바이더 선택은 다음 우선순위로 **첫 번째 매칭을 사용**한다.<br>① `client_id` 일치 + 입력 이메일 도메인 포함<br>② `client_id` 일치 + 도메인 조건 없음<br>③ `client_id` = NULL(전체) + 입력 이메일 도메인 포함<br>④ `client_id` = NULL(전체) + 도메인 조건 없음 |
| FR-7 | 위 4단계 중 어디에도 매칭되지 않으면 외부 인증을 수행하지 않고 **기존 로컬 비밀번호 인증 경로**로 진행한다. |
| FR-8 | 중복 등록 규칙을 다음과 같이 완화한다.<br>· 도메인 조건이 없는 프로바이더는 여전히 `(tenant_id, client_id)`당 **1개**만 허용<br>· 도메인 조건이 있는 프로바이더는 같은 `(tenant_id, client_id)` 범위 안에서 **도메인이 서로 겹치지 않는 한 여러 개** 등록 가능 |
| FR-9 | 도메인이 겹치는 프로바이더 등록·수정 시 409 Conflict를 반환하며, 응답 메시지에 **충돌한 도메인 값**을 포함한다. |
| FR-10 | 관리 웹 UI(프로바이더 등록/수정 폼)에서 적용 도메인 목록을 입력·편집할 수 있다. |
| FR-11 | 관리 웹 UI 목록 화면의 적용 범위 표시에 도메인 조건을 함께 노출한다. 예: `전체 클라이언트 · @test1.com, @test1.co.kr` |

## 4. 비기능 요구사항

- **하위호환**: 마이그레이션은 컬럼 추가만 수행하고 기존 행은 `null`(도메인 무관)로 남긴다. 기존 프로바이더의 동작은 100% 유지된다.
- **성능**: 프로바이더 선택은 로그인 경로의 동기 작업이므로 추가 DB 왕복을 최소화한다. 기존 인덱스 `(tenant_id, client_id)`를 그대로 활용한다.
- **예측 가능성**: 정규식 등 관리자가 실수하기 쉬운 매칭 방식은 채택하지 않는다(정확 일치만).
- **감사성**: 어떤 프로바이더가 선택되었는지는 기존 감사 로그의 `providerId` 메타데이터로 추적 가능해야 한다(기존 동작 유지).

## 5. 제외 범위 (Out of Scope)

- 와일드카드(`*.test.com`) 및 정규식 기반 도메인 매칭.
- 서브도메인 자동 상속 매칭.
- 관리자가 직접 지정하는 명시적 `priority` 컬럼(우선순위는 FR-6의 고정 규칙으로만 결정).
- 도메인 조건 미매칭 시 로그인을 거부하는 화이트리스트 동작.
- 이메일 외 다른 속성(예: IP, 사용자 그룹)에 의한 프로바이더 분기.
- 이미 로컬에 존재하는 사용자의 소속 도메인 재검증.

## 6. 성공 기준

- 하나의 테넌트에 도메인이 다른 프로바이더 2개(`@test1.com`, `@test2.com`)와 도메인 무관 프로바이더 1개를 동시에 등록할 수 있다.
- `user@test1.com`으로 로그인하면 `@test1.com` 프로바이더가, `user@test2.com`으로 로그인하면 `@test2.com` 프로바이더가 호출된다.
- `user@other.com`으로 로그인하면 도메인 무관 프로바이더가 호출되고, 그마저 없으면 로컬 비밀번호 인증이 수행된다.
- 같은 범위에 이미 등록된 도메인을 다시 등록하려 하면 409와 함께 충돌 도메인이 안내된다.
- 기존에 등록되어 있던 프로바이더는 마이그레이션 후에도 동일하게 동작한다.
- `bun run lint && bun run typecheck && bun run test && bun run build` 통과.
