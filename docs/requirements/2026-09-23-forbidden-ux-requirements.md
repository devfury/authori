# 요구사항정의서 — 권한 없는 접근을 화면에 드러내기

- 작성일: 2026-09-23
- 작성자: Jinho Lee
- 상태: 확정
- 유형: 결함 수정 (관리 UI / UX)

## 1. 문제 정의

테넌트 관리자가 **권한 없는 테넌트의 URL로 진입하면 화면이 정상처럼 렌더링된다.** 브라우저 콘솔에만 403 이 찍히고, 사용자에게는 데이터가 하나도 없는 빈 목록만 보인다. "데이터가 없는 테넌트"인지 "볼 권한이 없는 테넌트"인지 화면만 보고는 구분할 수 없다.

이는 [2026-09-23-tenant-admin-login-401](2026-09-23-tenant-admin-login-401-requirements.md) 작업에서 권한 부족 응답을 401 → 403 으로 바꾸면서 드러난 문제다. 이전에는 401 이 강제 로그아웃을 유발해 (잘못된 방식으로) 눈에 띄었지만, 403 으로 바뀐 뒤에는 아무 일도 일어나지 않는다. 해당 작업에서 "프런트엔드 403 전역 처리"를 제외 범위로 명시했고, 그 빈자리가 이번 증상이다.

### 1.1 원인

세 지점이 겹친다.

| # | 위치 | 문제 |
|---|---|---|
| 1 | `apps/web/src/router/index.ts:226` | 라우터 가드가 `requiresPlatformAdmin` 만 검사한다. **테넌트 경계는 검사하지 않는다.** `/admin/tenants/:tenantId/*` 라우트는 `meta: { requiresAuth: true }` 뿐이라, 테넌트 A 관리자가 테넌트 B 의 URL 로 들어가도 가드를 통과해 화면이 렌더링된다. |
| 2 | 테넌트 화면 다수 | 목록·상세 로딩이 `try { ... } finally { loading = false }` 형태로 **`catch` 가 없다.** API 가 403 을 던져도 조용히 삼켜지고 빈 화면만 남는다. 403 뿐 아니라 500·네트워크 오류에서도 동일하다. |
| 3 | `apps/web/src/views/ForbiddenView.vue` | "홈으로 돌아가기" 링크가 `/admin` 을 가리킨다. 이 경로는 `requiresPlatformAdmin: true` 라 **테넌트 관리자가 누르면 다시 403 으로 돌아온다.** 빠져나갈 수 없는 막다른 골목이다. |

### 1.2 영향 범위

`try` 는 있으나 `catch` 가 없어 오류를 삼키는 화면 9곳:

`DashboardView`, `ClientListView`, `UserListView`, `RoleListView`, `PermissionListView`, `ScopeListView`, `SchemaListView`, `AuditLogView`, `ExternalAuthListView`

## 2. 목표

1. 권한 없는 테넌트로 진입하면 **화면이 그려지기 전에** 차단하고 권한이 없음을 명시한다.
2. 라우터가 걸러내지 못한 개별 API 오류도 빈 화면이 아니라 **이유가 보이는 화면**으로 끝난다.
3. 403 화면에서 자기 권한 범위로 되돌아갈 수 있다.

## 3. 기능 요구사항

| ID | 요구사항 |
|---|---|
| FR-1 | 라우터 가드가 경로의 `tenantId` 파라미터와 로그인 사용자의 테넌트를 대조한다. TENANT_ADMIN 이 자기 테넌트가 아닌 경로로 진입하면 403 페이지로 보낸다. |
| FR-2 | PLATFORM_ADMIN 은 모든 테넌트 경로에 진입할 수 있다(기존 동작 유지). |
| FR-3 | 403 차단은 **화면 렌더링과 API 호출 이전**에 일어난다. 불필요한 요청을 보내지 않는다. |
| FR-4 | 403 페이지의 복귀 링크는 역할에 맞는 목적지를 가리킨다. PLATFORM_ADMIN → 테넌트 목록, TENANT_ADMIN → 자기 테넌트 대시보드. 테넌트를 알 수 없으면 로그인 화면. |
| FR-5 | 목록·상세 화면의 데이터 로딩이 실패하면 빈 화면 대신 오류 상태를 표시한다. |
| FR-6 | 오류 메시지는 원인에 따라 구분한다. 403 은 "권한이 없습니다", 404 는 "찾을 수 없습니다", 그 외(500·네트워크)는 "불러오지 못했습니다". |
| FR-7 | 오류 표시와 메시지 매핑은 **공용 컴포넌트·공용 유틸 한 곳**에서 담당한다. 화면마다 문구와 모양이 갈라지지 않게 한다. |
| FR-8 | 401(인증 만료)은 기존대로 전역 인터셉터의 로그아웃으로 처리한다. 오류 배너 대상이 아니다. |

## 4. 비기능 요구사항

| ID | 요구사항 |
|---|---|
| NFR-1 | 백엔드 변경 없음. 프런트엔드만 수정한다. |
| NFR-2 | 라우터 가드는 **서버 인가의 대체물이 아니라 UX 장치**다. 서버의 `TenantAdminGuard` 검사는 그대로 유지되며, 프런트 가드가 뚫려도 보안 경계는 서버가 지킨다. |
| NFR-3 | 오류 상태의 시각적 톤은 기존 화면(카드·간격·색)과 일치시킨다. |
| NFR-4 | 라우터 가드와 오류 메시지 매핑은 단위 테스트로 검증한다(vitest + @vue/test-utils). |

## 5. 제외 범위

- **`http.ts` 인터셉터의 403 전역 리다이렉트** — 설정 저장 시 `status` 변경 거부처럼 **인라인으로 보여야 할 403** 까지 화면을 날려버린다. 오류 표시는 호출 지점이 결정한다.
- **폼 제출·다이얼로그의 오류 처리 개편** — 이미 `catch` 로 인라인 오류를 표시하고 있다. 본 작업은 `catch` 가 없어 **조용히 실패하는** 조회 경로만 다룬다.
- **사이드바 메뉴의 동적 권한 필터링** — 플랫폼 메뉴는 이미 `isPlatformAdmin` 으로 숨겨져 있다. 테넌트 메뉴는 현재 테넌트 기준이라 추가 필터가 필요 없다.
- **재시도 버튼의 자동 백오프·재시도 횟수 제한** — 단순 재호출로 충분하다.
- **백엔드 인가 로직** — 직전 작업에서 완료했다.

## 6. 성공 기준

- 테넌트 A 관리자가 `/admin/tenants/<B의 id>/users` 로 진입하면 403 화면이 뜨고, 네트워크 탭에 해당 테넌트 API 요청이 **한 건도 없다.**
- 403 화면의 복귀 링크를 누르면 테넌트 관리자는 자기 대시보드로 간다(다시 403 으로 튕기지 않는다).
- 플랫폼 관리자는 모든 테넌트 화면에 기존대로 진입한다.
- 목록 화면에서 서버 오류·네트워크 단절이 발생하면 빈 목록이 아니라 이유가 적힌 오류 상태가 보인다.
- `bun run lint`, `bun run typecheck`, `bun run test`, `bun run build` 통과(lint 는 기존 baseline 대비 신규 유입 0건).
