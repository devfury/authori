# 요구사항정의서 — 한 관리자가 여러 테넌트를 관리

- 작성일: 2026-09-23
- 작성자: Jinho Lee
- 상태: 확정
- 유형: 기능 개발 (인가 모델 / 데이터 모델 / 관리 UI)

## 1. 문제 정의

현재 **TENANT_ADMIN 은 단 하나의 테넌트에만 속할 수 있다.** `admin_users.tenant_id` 가 단일 nullable uuid 컬럼이고(`admin-user.entity.ts:39`), 이 1:1 전제가 전 계층에 박혀 있다.

| 계층 | 1:1 전제 |
|---|---|
| 엔티티 | `admin_users.tenant_id` 단일 컬럼 |
| JWT | 페이로드에 `tenantId` 하나 |
| 서버 가드 | `TenantAdminGuard` 가 `admin.tenantId === paramTenantId` 등치 비교 |
| 로그인 흐름 | `auth.store.ts` 가 그 테넌트 대시보드로 직행 |
| 프런트 가드 | `auth.tenantId !== to.params.tenantId` 등치 비교 |
| 관리 UI | 관리자 생성·수정 화면의 테넌트 **단일 선택** 드롭다운 |

여러 테넌트를 맡은 담당자는 테넌트 수만큼 **별도 계정을 만들어 번갈아 로그인**해야 한다. 계정·비밀번호가 분산되고, 감사 로그에서도 동일 인물의 행위가 여러 주체로 흩어진다.

### 1.1 유리한 조건

관리 화면과 라우팅은 이미 `/admin/tenants/:tenantId/*` 로 **경로 파라미터 기반**이다. 화면 자체는 어떤 테넌트든 그릴 수 있다. 바꿔야 할 것은 "몇 개를 허용하는가"와 "어떻게 전환하는가"이지, 화면 구조가 아니다.

## 2. 목표

1. 한 관리자 계정에 **여러 테넌트를 배정**할 수 있다.
2. 그 관리자가 로그인 후 **테넌트를 오가며** 관리할 수 있다.
3. 배정되지 않은 테넌트는 **서버에서** 차단된다.

## 3. 확정된 설계 결정

사전 논의로 확정한 사항이다. 근거를 함께 남긴다.

| # | 결정 | 근거 |
|---|---|---|
| D-1 | **모든 소속 테넌트에 동일 권한.** 테넌트별 역할 차등은 두지 않는다. | 매핑이 `(admin_id, tenant_id)` 두 컬럼으로 끝나 단순하다. 차등이 필요해지면 컬럼 추가로 확장할 수 있고, 지금 넣으면 가드가 "소속 여부"가 아니라 "무슨 권한으로"까지 판정해야 해 범위가 커진다. |
| D-2 | **로그인 직후 선택 화면 + 상시 전환 드롭다운을 모두 제공.** | 소속이 여러 개일 때 맥락을 명확히 하면서, 전환할 때마다 선택 화면을 거치지 않아도 된다. 소속이 1개면 선택 화면을 건너뛰어 기존 경험이 그대로 유지된다. |
| D-3 | **접근 가능한 테넌트 목록을 JWT 에 담지 않는다.** 서버 가드가 DB 를 조회해 판정한다. | 권한 회수가 즉시 반영된다. 토큰에 담으면 배정을 해제해도 기존 토큰이 만료될 때까지 접근이 유지된다. 토큰 크기도 소속 수에 비례해 커지지 않는다. 대가는 가드마다 조회 1회이나, 인덱스된 2컬럼 테이블이라 부담이 작다. |

## 4. 기능 요구사항

### 4.1 데이터 모델

| ID | 요구사항 |
|---|---|
| FR-1 | 관리자와 테넌트의 **N:M 매핑 테이블**을 둔다. |
| FR-2 | 매핑은 관리자·테넌트 삭제 시 함께 정리된다(고아 행이 남지 않는다). |
| FR-3 | 같은 (관리자, 테넌트) 조합이 중복 저장되지 않는다. |
| FR-4 | `admin_users.tenant_id` 는 **제거한다.** 같은 사실에 대한 출처를 둘로 두지 않는다. |
| FR-5 | 기존 TENANT_ADMIN 의 `tenant_id` 값은 마이그레이션으로 매핑 테이블에 이관된다. 데이터 손실이 없다. |

### 4.2 인가

| ID | 요구사항 |
|---|---|
| FR-6 | `TenantAdminGuard` 는 경로의 `:tenantId` 가 **요청자에게 배정된 테넌트인지** DB 로 확인한다. |
| FR-7 | PLATFORM_ADMIN 은 기존대로 모든 테넌트에 접근한다. |
| FR-8 | 배정되지 않은 테넌트 접근은 403 으로 거부된다. |
| FR-9 | 배정을 해제하면 **기존 발급 토큰으로도 즉시 차단**된다(D-3). |
| FR-10 | JWT 페이로드에서 `tenantId` 를 제거한다. 남겨두면 쓰이지 않는 값이 사실처럼 보인다. |

### 4.3 관리자 계정 관리 (PLATFORM_ADMIN)

| ID | 요구사항 |
|---|---|
| FR-11 | 관리자 생성 시 테넌트를 **여러 개 배정**할 수 있다. |
| FR-12 | 관리자 수정 시 배정 테넌트를 추가·제거할 수 있다. |
| FR-13 | TENANT_ADMIN 은 **최소 1개** 테넌트가 배정돼야 한다. 0개는 거부한다. |
| FR-14 | PLATFORM_ADMIN 에게는 테넌트를 배정하지 않는다(모든 테넌트 접근이 역할에 내재). |
| FR-15 | 존재하지 않거나 비활성 테넌트 배정은 거부한다. |
| FR-16 | 관리자 목록·상세에 배정된 테넌트가 표시된다. |

### 4.4 로그인과 테넌트 전환

| ID | 요구사항 |
|---|---|
| FR-17 | 로그인 응답이 **접근 가능한 테넌트 목록**(id·slug·name)을 함께 내려준다. |
| FR-18 | 소속이 1개면 로그인 후 그 테넌트 대시보드로 **바로** 이동한다(현재 동작 유지). |
| FR-19 | 소속이 2개 이상이면 로그인 후 **테넌트 선택 화면**을 보여준다. |
| FR-20 | 소속이 2개 이상이면 사이드바에서 **언제든 테넌트를 전환**할 수 있다. 1개면 지금처럼 이름만 표시한다. |
| FR-21 | 전환하면 같은 성격의 화면을 유지한 채 테넌트만 바뀐다(사용자 목록에서 전환 → 새 테넌트의 사용자 목록). 유지할 수 없으면 대시보드로 보낸다. |
| FR-22 | 프런트 라우터 가드는 배정된 테넌트 **목록에 포함되는지**로 판정한다(기존 등치 비교 대체). |
| FR-23 | PLATFORM_ADMIN 의 로그인 흐름은 변경하지 않는다(테넌트 목록으로 이동). |

## 5. 비기능 요구사항

| ID | 요구사항 |
|---|---|
| NFR-1 | **서버가 인가의 단일 진실**이다. 프런트 가드·전환 UI 는 UX 장치이며, 우회해도 서버가 차단한다. |
| NFR-2 | 마이그레이션은 무중단 배포를 전제하지 않는다. 컬럼 제거가 포함되므로 **배포와 마이그레이션 시점을 함께** 다뤄야 한다. 이 제약을 설계서에 명시한다. |
| NFR-3 | 마이그레이션 down 경로는 단일 컬럼으로 되돌리므로 **2개 이상 배정된 관리자에서 정보 손실이 불가피**하다. 손실 규칙을 문서에 명시한다. |
| NFR-4 | 가드의 추가 조회는 인덱스를 사용한다. |
| NFR-5 | 인가 규칙 변경은 단위 테스트로 검증한다(소속/비소속/플랫폼 관리자/배정 해제 직후). |
| NFR-6 | 기존 단일 테넌트 관리자의 체감 동작이 바뀌지 않는다(선택 화면·드롭다운 모두 건너뜀). |

## 6. 제외 범위

- **테넌트별 역할 차등** — D-1. 모든 소속 테넌트에 동일 권한.
- **관리자 본인의 테넌트 배정 변경** — 배정은 PLATFORM_ADMIN 고유 권한으로 유지한다.
- **테넌트 간 데이터 통합 조회**(여러 테넌트의 사용자를 한 화면에서) — 전환 모델로 충분하며, 통합 조회는 별개의 큰 기능이다.
- **관리자 계정 변경의 감사 로그** — 현재 `AdminAuthService` 는 `AuditService` 를 쓰지 않아 관리자 생성·수정이 아예 감사되지 않는다. **기존부터 있던 공백**이며, 테넌트 배정 변경은 감사 가치가 높으므로 후속 작업으로 분리해 제안한다. 본 작업에서 감사 체계를 새로 들이면 범위가 두 배가 된다.
- **PLATFORM_ADMIN 의 권한 모델 변경** — 그대로.
- **테넌트 전환 시 진행 중이던 폼 상태 보존** — 전환은 페이지 이동으로 취급한다.

## 7. 성공 기준

- 한 관리자 계정에 테넌트 2개 이상을 배정할 수 있고, 로그인하면 선택 화면이 뜬다.
- 선택 후 해당 테넌트의 화면이 정상 동작하며, 사이드바 드롭다운으로 다른 테넌트로 전환된다.
- 배정되지 않은 테넌트 ID 로 API 를 직접 호출하면 403 이 반환된다.
- **배정을 해제한 직후, 기존에 발급된 토큰으로 호출해도 403** 이 반환된다(FR-9).
- 기존 단일 테넌트 관리자는 마이그레이션 후에도 로그인 시 곧바로 자기 대시보드로 이동한다.
- 기존 PLATFORM_ADMIN 동작에 변화가 없다.
- `bun run lint`(기존 baseline 대비 신규 유입 0건), `bun run typecheck`, `bun run test`, `bun run build` 통과.
