# 요구사항정의서 — 승인 대기 신규 가입자 ezAria 알림

- 작성일: 2026-08-23
- 작성자: Jinho Lee
- 상태: 초안 (승인 대기)

## 1. 문제 정의

공개 회원가입(`TenantSettings.allowRegistration`)이 켜져 있고 **자동 활성화(`autoActivateRegistration`)와 이메일
인증(`emailVerificationRequired`)이 모두 꺼져 있으면**, 신규 가입자는 `apps/api/src/oauth/authorize/authorize.service.ts`의
`register()`에서 `UserStatus.INACTIVE`로 생성되고 **관리자가 직접 활성화해 줄 때까지 로그인할 수 없다.**

- 이 시점에 관리자에게 전달되는 알림이 **하나도 없다.** 관리자가 우연히 관리 UI의 사용자 목록을 열어보지 않으면
  가입자는 사실상 무한히 대기한다.
- 현재 저장소에는 메일(`common/mail/MailService`) 외에 어떤 알림 채널도 없다.
- 가입 순간의 알림만으로는 부족하다. 알림을 놓치면 대기 상태가 다시 방치되기 때문에 미처리 잔량을 다시 알려 주는
  백스톱이 필요하다.

## 2. 목표

- 관리자 승인이 필요한 신규 가입이 발생하면 **가입 즉시** 테넌트 담당자의 ezAria 채팅방으로 알린다.
- 승인 대기 건이 남아 있으면 **매일 정해진 시각에 잔량을 다시 알려** 무한 대기를 구조적으로 방지한다.
- 알림 설정(수신 채팅방, on/off)은 **테넌트별로** 관리하며 관리 UI에서 변경할 수 있게 한다.
- 알림 실패가 회원가입 자체를 실패시키지 않는다.

## 3. 사용자·역할 범위

| 역할 | 관련 동작 |
|---|---|
| 엔드유저(가입자) | 공개 회원가입 요청. 알림 내용에 마스킹된 이메일로만 등장한다. |
| 테넌트 관리자(TENANT_ADMIN) | 자기 테넌트의 알림 on/off·수신 채팅방 설정, 테스트 발송, 대기 사용자 활성화 |
| 플랫폼 관리자(PLATFORM_ADMIN) | 모든 테넌트에 대해 위 동작 수행 |
| 운영자 | 전역 ezAria 봇 토큰·API base URL·관리 UI base URL을 `.env`로 설정 |

## 4. 기능 요구사항

| ID | 요구사항 |
|----|----------|
| FR-1 | `TenantSettings`에 알림 사용 여부(`pendingApprovalNotifyEnabled`, 기본 `false`)와 수신 채팅방(`ezariaChatRoomId`, nullable)을 추가한다. |
| FR-2 | ezAria 봇 토큰과 봇 API base URL은 전역 환경변수(`EZARIA_BOT_TOKEN`, `EZARIA_BOT_BASE_URL`)로 관리한다. 비밀정보인 토큰은 로그·API 응답에 노출하지 않는다. |
| FR-3 | 알림 링크용 관리 UI base URL을 환경변수(`ADMIN_BASE_URL`)로 설정한다. 미설정 시 `LOGIN_PAGE_URL`의 origin을 사용한다. |
| FR-4 | 공개 회원가입 결과가 **관리자 승인 대기 INACTIVE**인 경우(= `emailVerificationRequired=false` ∧ `autoActivateRegistration=false`), 가입 성공 직후 해당 테넌트의 ezAria 채팅방으로 알림 1건을 발송한다. |
| FR-5 | 매일 09:00(Asia/Seoul)에 알림이 켜진 테넌트별로 승인 대기 사용자를 집계하여, **1건 이상이면** 잔량 다이제스트를 발송한다. 0건이면 발송하지 않는다. |
| FR-6 | 승인 대기 집계 대상은 관리자 승인 대기 사용자로 한정한다. 이메일 인증 대기, 관리자가 직접 생성한 INACTIVE, 탈퇴(`deactivatedAt IS NOT NULL`) 사용자는 제외한다. |
| FR-7 | FR-6의 구분을 위해 `users` 테이블에 `pendingApprovalSince`(timestamptz, nullable)를 추가한다. 승인 대기로 생성될 때 기록하고 활성화 시 `null`로 지운다. |
| FR-8 | 알림 메시지의 가입자 이메일은 부분 마스킹한다(예: `jinho@ez.com` → `j***@ez.com`). 원본 이메일은 알림에 넣지 않는다. |
| FR-9 | 알림 메시지에는 테넌트명, 마스킹된 이메일, 가입 시각(KST), 현재 승인 대기 건수, 관리 UI 승인 화면 링크를 포함한다. 다이제스트에는 최장 대기 경과일을 추가한다. |
| FR-10 | 알림 발송 실패(네트워크 오류, HTTP 오류, 타임아웃)는 회원가입 처리와 다이제스트 순회를 중단시키지 않는다. 오류는 로그로 남긴다. |
| FR-11 | 봇 토큰 미설정, 알림 비활성, 채팅방 ID 미설정 중 하나라도 해당하면 발송을 건너뛴다(SMTP 미설정 폴백과 동일한 방식으로 로그만 남긴다). |
| FR-12 | 테넌트 설정 저장 API에서 FR-1의 두 필드를 저장할 수 있고, 관리 UI 테넌트 설정 화면에 `ezAria 알림` 섹션(사용 토글, 채팅방 ID 입력)을 제공한다. |
| FR-13 | 설정한 채팅방 ID가 유효한지 확인할 수 있도록 테스트 발송 API와 관리 UI 버튼을 제공한다. 테스트 발송은 감사 로그에 기록한다. |
| FR-14 | 다이제스트는 여러 API 인스턴스가 동시에 실행되어도 중복 발송하지 않는다(기존 `AccountDeletionSweepService`와 동일한 PostgreSQL advisory lock 방식). |

## 5. 비기능 요구사항

- **격리**: 회원가입 경로에 추가되는 외부 HTTP 호출은 타임아웃(5초)과 `try/catch`로 감싸 가입 응답 지연·실패를 유발하지 않는다.
- **하위호환**: 기존 테넌트는 알림이 꺼진 상태(`false` + `null`)로 마이그레이션되며 동작 변화가 없다.
- **개인정보**: ezAria 채팅방은 서비스 외부 저장소이므로 가입자 이메일 원문·프로필 값을 보내지 않는다.
- **마이그레이션 안전성**: `pendingApprovalSince` 추가 시 기존 승인 대기 사용자는 `created_at` 값으로 백필해 첫 다이제스트부터 집계에 포함된다.
- **테스트 가능성**: ezAria HTTP 호출은 주입 가능한 클라이언트로 분리해 단위 테스트에서 모킹한다.

## 6. 제외 범위 (Out of Scope)

- 이메일 인증 미완료 가입자에 대한 알림·독촉.
- 관리자가 관리 UI에서 직접 생성한 INACTIVE 사용자에 대한 알림.
- 이메일·슬랙 등 ezAria 이외 채널로의 알림 확장.
- 알림 전송 보장을 위한 outbox 테이블·재시도 워커(일일 다이제스트가 백스톱 역할을 한다).
- 테넌트별 알림 주기·시각 커스터마이징(전역 09:00 고정).
- 알림 메시지에서 바로 승인하는 인터랙션(버튼/콜백).
- 가입자 본인에게 "승인 대기 중" 안내 메일 발송.

## 7. 성공 기준

- 자동 활성화·이메일 인증이 모두 꺼진 테넌트에서 회원가입하면 해당 테넌트 ezAria 채팅방에 알림이 도착하고, 이메일이 마스킹되어 있다.
- 승인 대기 건이 남아 있는 동안 매일 09:00 다이제스트가 도착하고, 모두 활성화하면 다음 날 알림이 오지 않는다.
- 알림이 꺼진 테넌트나 봇 토큰 미설정 환경에서는 알림이 발송되지 않고 가입은 정상 동작한다.
- ezAria 서버가 응답하지 않아도 회원가입 API는 정상(2xx) 응답한다.
- 관리 UI에서 채팅방 ID를 저장하고 테스트 발송 버튼으로 도착을 확인할 수 있다.
- `bun run lint && bun run typecheck && bun run test && bun run build` 통과.
